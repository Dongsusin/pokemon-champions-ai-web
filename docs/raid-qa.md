# 협동 보스전 로컬 검증 기록

기준일: 2026-09-14. 구현 기준은 사용자 첨부 `pokemon_champions_coop_boss_raid_codex_prompt.txt`이며, 레이드 규칙/엔진/저장 스키마 버전은 각각 1이다. 이 작업은 `codex/battle-factory` 브랜치에서 수행했고 운영 배포·DB 변경·환경변수 활성화는 하지 않는다.

## 직접 플레이하는 로컬 실행기

```sh
npm run raid:test
```

실행기는 `127.0.0.1:5187`의 화면과 `127.0.0.1:8789`의 레이드 HTTP 서버를 함께 시작한다. 두 포트를 이미 다른 프로그램이 사용하면 실행을 종료하므로 해당 포트를 비운 뒤 다시 시작한다. 일반 Vite 개발 서버와 구분되는 `raid-test` 모드이며 환경 파일을 수정하지 않는다.

- `http://127.0.0.1:5187/raid-test.html?player=alice`
- `http://127.0.0.1:5187/raid-test.html?player=bob`
- `http://127.0.0.1:5187/raid-test.html?player=charlie`

각 화면에서 시작하기 → 협동 보스전으로 들어간다. 여러 사람을 확인할 때는 일반 탭 세 개 대신 **저장소가 분리된 브라우저 프로필**을 사용한다. 같은 브라우저의 일반 탭과 여러 시크릿 창은 서로 저장소를 공유할 수 있다. 한 계정으로 시작하면 NPC가 나머지 자리를 채운다.

테스트 계정은 로컬 실행기에서만 허용하고 실제 Firebase 로그인은 실행하지 않는다. 준비된 보유 개체도 로컬 서버가 확인하며 전투는 실제 레이드 엔진으로 계산한다. 테스트용 방·전투·보상 기록은 메모리에만 저장하고 `Ctrl+C`로 종료하면 사라진다. 브라우저에 표시되는 테스트 VP는 운영 계정으로 전달되지 않는다.

위 검증은 Node.js 24, 별도 메모리 저장소, 합성된 인증 ID로 진행한다. HTTP 핸들러 검증은 실제 요청/응답 형식과 서버 명령 경로를 실행하지만 운영 Firebase OAuth나 Supabase 연결의 성공을 뜻하지 않는다. 참가자는 서로 다른 UID와 별도 계정 저장을 사용한다. 운영 API에 강제 HP·강제 보상·테스트 계정 경로를 추가하지 않는다.

`validateRaidJourneys.mjs`는 임의 HP/종족값 변경 없이 합법적인 보유 개체를 고르고 전초전부터 결과까지 진행한다. 모든 실행에서 서버 재생성 후 같은 상태 복원, 참가자 간 HP·폼·턴 일치, 각자 동시 제출, 비밀 값 없는 응답, 방/포인터 종료, 결과 재조회와 보상 멱등, 영구 보유 개체의 불변성을 검사한다. 승리한 실행은 참가자별 300 VP + 해당 보스 최초 500 VP가 한 번만 정산되는지 확인한다.

### HTTP 여정의 관찰 결과

| 보스 / 참가 포켓몬 | 사람 1명 + NPC 2명 | 사람 2명 + NPC 1명 | 사람 3명 |
| --- | --- | --- | --- |
| 뮤츠 / 마기라스 | 패배, 16턴 | 패배, 11턴 | 패배, 10턴 |
| 칠색조 / 가이오가 | 패배, 8턴 | 패배, 5턴 | 패배, 5턴 |
| 루기아 / 미라이돈 | 패배, 13턴 | 승리, 10턴 | 승리, 12턴 |

모두 실제 2단계에 진입했다. 같은 종을 중복 선택한 특정 팀과 자동 명령 정책의 관찰값이며 사람의 전략을 반영한 승률이나 밸런스 보증이 아니다. 지원 기술/장비/상성 조합을 달리하는 추가 플레이가 필요하다. 서비스 여정은 서비스 요청별 seed를 사용하므로 [순수 엔진 시뮬레이션](raid-rules.md)의 seed 및 결과와 다르다.

실행 때마다 아래 로컬 산출물을 갱신한다. `.cache`는 Git에서 제외한다.

- `scripts/.cache/raid-mechanics/simulations.json`: 엔진 seed, 인원, 결과, 턴, 이벤트 후 상태, 순수 턴 계산 시간.
- `scripts/.cache/raid-journeys/results.json`: HTTP 여정 seed, 인원, 단계, 결과, 요청 수, p50/p95 처리 시간.
- `scripts/.cache/raid-ui/report.json`: 화면 흐름 9개 검사, 브라우저/API 오류, 데스크톱·모바일·2배 글자 크기의 DOM 경계와 PNG.
- `scripts/.cache/raid-three-clients/report.json`: 세 보스의 독립 브라우저 간 상태 비교, 결과 지급·재접속 검사와 보스별 PNG.

지연 측정은 로컬 메모리 저장소의 요청 처리 시간이며 인터넷·실제 DB·서버리스 콜드 스타트 비용을 포함하지 않는다. 관측 지연을 운영 성능으로 보고하지 않는다.

### 실제 GameApp 수동 확인

`raid:test` 실행기의 Charlie 계정으로 기존 메인 화면에서 시작하기 → 협동 보스전 → 루기아 → 솔로 도전 → 미라이돈 선택 → 준비 완료 → 전초전 진입을 직접 확인했다. 준비 시 서버가 확인하는 capture ID와 GameApp의 도감 정규화 ID가 다르던 테스트 실행기 문제를 수정한 뒤 같은 흐름을 다시 통과했다.

전초전 종료 후 같은 세 아군의 HP·PP를 회복해 본체전에 진입했고, HP 50%의 다크루기아 외형·고정 비, 참가자 테라스탈, HP 25%에서 최대 HP 1,704 → 2,556의 생명력 증가를 실제 화면에서 확인했다. 철수 결과는 0 VP로 표시됐으며 결과를 닫으면 새 보스 선택 로비로 돌아왔다. 이 확인은 Codex 브라우저와 로컬 HTTP 서버에서 수행했으며 실제 운영 계정이나 실물 휴대전화 검증이 아니다.

### 독립 브라우저 3개와 화면 검증

Playwright의 저장소가 분리된 세 컨텍스트가 실제 `RaidScreen`과 loopback HTTP 서버를 사용했다. 전투 HP나 폼을 강제로 수정하지 않고 실제 합법적인 개체와 명령으로 진행했다. 뮤츠/화강돌 팀은 아머드 뮤츠 구간, 칠색조/가이오가 팀은 첫 소환 구간을 확인한 뒤 패배했다. 루기아/미라이돈 팀은 다크루기아와 25% 구간을 지나 승리했고 세 참가자 모두 800 VP를 받았다. 일반 승리 및 최초 클리어 영수증은 합계 6개이며 결과 전용 재로드와 닫기 후에도 늘어나지 않았다.

매 턴 세 클라이언트의 HP·최대 HP·폼·턴·결과·VP를 비교했다. 보스·소환수·아군 카드가 겹치지 않고 명령 영역이 뷰포트 안에 놓이는지도 검사했다. 일반 공격의 실제 적용 피해 수치는 impact 이벤트로, HP 보호로 차단된 초과 피해는 별도 이벤트로 전달한다.

화면은 1440×900, 1280×720, 1120×760, 1024×768의 글자 크기 2배, 가로 모바일 844×390/932×430에서 확인했다. 태블릿 2배 글자는 세부 패널 안에서 스크롤하고 준비·나가기 버튼에 접근할 수 있다. 모바일 전투는 상단 상태·적·아군·행동 버튼을 화면 안에 배치하며 전투 로그를 접을 수 있다. 이 검증에서 브라우저 애플리케이션 오류와 실패한 레이드 HTTP 요청은 없었다.

## 기존 기능 회귀

- 전투 상태 검사: 847개 기술의 2,541개 상황과 313개 특성의 626개 상황, 합계 14,357턴에서 HP/PP/랭크/유한 수치/교체/입력 불변성 통과.
- 특성·상태·도구·대상·교대·광역기·테라버스트·기믹 시점·사망 후 대상 재지정 등 관련 개별 엔진 회귀 통과.
- 팩토리 15개, 레이팅 VP 지갑 20개, 계정 API 클라이언트 9개, 계정 서비스 13개 및 업적 지갑 회귀 통과.
- 레이팅 서비스 51개, 대전방 21개, 대전방 관전 10개, 게스트 삭제 16개 회귀 통과.
- Postgres 저장 어댑터 16개와 저장소 이전 변환 8개 회귀 통과. Postgres 실서버 통합 검사는 실행하지 않았다.

`validate:guest-online`은 별도 서비스 계정 경로를 필수로 요구해 실제 인증 검사를 실행하지 않았다. 운영 계정이나 비밀값을 사용해 이 로컬 작업의 검증 범위를 확장하지 않는다.

전체 `npm run validate:battle-audit`는 `validateBattleMoveEffects.mjs:179`의 기존 회복봉인 검사에서 `36 !== 127`로 중단된다. 변경 전 HEAD의 `src/data/battleEngine.js`를 별도로 읽어 같은 검사에 주입해 동일 실패를 확인했다. 이 기존 실패를 새 레이드 실패로 집계하거나, 개별 검사 통과를 전체 감사 통과로 표현하지 않는다.

## 기능 플래그와 배포 경계

- 프런트: `VITE_RAID_ENABLED=false`가 기본이며 꺼진 일반 빌드에서는 허브 진입점을 표시하지 않는다.
- 서버: `RAID_ENABLED=false`가 기본이며 꺼진 API는 503을 반환한다. 프런트 플래그만으로 서버를 활성화할 수 없다.
- 주소: `VITE_RAID_API_URL=/api/raid`. Firebase 인증과 현재 게임 저장소 설정을 재사용하며 새 인증 제공자를 만들지 않는다.
- Vercel의 현재 작업 브랜치 자동 배포는 `vercel.json`에서 비활성화되어 있다. 커밋/원격 브랜치 푸시는 운영 배포와 구분한다.
- 운영 활성화 전에는 별도 승인된 환경에서 실제 인증/DB 경합·콜드 스타트·실물 모바일을 확인해야 한다. 이 로컬 작업에서는 해당 운영 검증을 수행했다고 주장하지 않는다.
