# 레이팅 배틀 로컬 테스트

이번 구현은 별도 브랜치 `codex/ranked-battles`에서 테스트한다. 운영 배포, 원격 푸시, 운영 환경변수 변경은 하지 않는다. 기본 환경에서는 클라이언트 참가 기능과 서버 API 모두 비활성화되어 있다.

## 실행

```powershell
npm install
npm run ranked:test
```

`http://127.0.0.1:5185`를 두 개의 브라우저 창 또는 탭에서 연다. 두 창 모두 **레이팅 배틀**로 들어간 뒤 하나는 **Alice**, 다른 하나는 **Bob**을 선택한다. 같은 배틀 형식을 고르고 **대전 상대 찾기**를 누른다. 준비된 두 종류의 팀을 사용할 수 있다.

선출 화면에서 출전할 포켓몬을 순서대로 선택하고 확정한다. 두 사용자가 모두 행동을 제출해야 서버에서 턴이 진행된다. 볼트체인지 같은 교체 기술이나 기절로 교대가 필요하면 해당 사용자가 다음 포켓몬을 직접 고른다. 상대가 검색 중이지 않으면 AI로 대신 매칭하지 않는다.

- 프런트엔드: `127.0.0.1:5185`, 백엔드: `127.0.0.1:8787`.
- 종료: 실행한 터미널에서 `Ctrl+C`.
- 테스트 계정 선택은 각 탭의 세션에 저장된다. 새로고침 후 레이팅 배틀에 다시 들어가면 진행 중인 경기를 복구한다.
- 결과는 Git에서 제외한 `scripts/.cache/ranked-test/state.json`에 저장된다. 정상 종료 후 재실행해도 기록이 유지된다.
- 같은 파일을 사용하는 서버를 동시에 실행할 수 없다. 비정상 강제 종료로 잠금 파일이 남으면 저장된 PID의 종료를 확인한 경우에만 자동 복구한다. 살아 있거나 확인할 수 없는 PID의 잠금은 유지한다.
- 테스트 실행 명령은 현재 프로세스에만 로컬 전용 플래그를 적용한다. 실제 Google 계정이나 운영 Firestore에 접속해서 기록을 쓰지 않는다.
- 이 주소는 같은 컴퓨터에서만 접속할 수 있다. 다른 기기·외부 사용자와의 테스트는 별도의 인증된 테스트 서버 설정이 필요하다.

## 경기와 등급

| 형식 | 등록 | 선출 | 동시 출전 |
| --- | --- | --- | --- |
| 싱글 | 6마리 | 3마리 | 1마리 |
| 더블 | 6마리 | 4마리 | 2마리 |

모두 Lv.50이며 같은 종과 같은 도구의 중복 등록을 제한한다. 상대의 등록 포켓몬 6마리는 미리 보이지만 선출 순서, 아직 등장하지 않은 선출 포켓몬, 미사용 기술·도구·특성·테라타입·능력치는 공개하지 않는다. 현재 게임에서 구현한 배틀 기믹을 사용할 수 있으며, 공식 시즌별 참가 제한이나 기믹 제한을 그대로 복제한 규정은 아니다.

| 등급 | RP | 세부 단계 |
| --- | --- | --- |
| 몬스터볼 | 0–399 | IV → III → II → I |
| 슈퍼볼 | 400–799 | IV → III → II → I |
| 하이퍼볼 | 800–1199 | IV → III → II → I |
| 마스터볼 | 1200 이상 | 레이팅 점수 표시 |

승리 +30 RP, 패배 −15 RP, 무승부 0 RP이며 최저 0 RP다. 100 RP마다 세부 단계가 바뀌고 패배하면 강등될 수 있다. 매칭용 레이팅은 1000에서 시작하는 Elo(K=32)로 계산한다. 상대 레이팅에 따라 변화량이 달라진다. 싱글과 더블의 등급·전적·레이팅은 별개다. 이 수치는 테스트를 위한 자체 규칙이다.

등급 구성과 등록 후 선출 흐름을 참고한 공식 자료: [Pokémon Champions 시즌 규정](https://web-view.app.pokemonchampions.jp/battle/pages/events/rd178289865727xkrgpg/en/event.html).

## 서버 판정과 복구

- 서버가 정식 포켓몬·기술 데이터로 팀을 다시 구성한다. 클라이언트가 전달한 능력치, 기술 위력, 승패를 그대로 사용하지 않는다.
- 제출한 행동은 두 사용자 모두 준비될 때까지 상대에게 공개하지 않는다. 각 사용자는 자신이 아래쪽에 보이는 동일한 배틀 UI를 사용한다.
- 인증된 경기 참가자만 조회·선출·명령·교체·기권을 할 수 있다. 경기 버전과 요청 식별자를 검사하고 결과를 두 계정에 한 번만 정산한다.
- 대기열은 30초 동안 갱신되지 않으면 만료된다. 매칭 범위는 레이팅 차이 100부터 대기 시간에 따라 최대 800까지 넓어진다.
- 선출 90초, 행동 60초, 교체 45초. 연출이 있는 턴에는 최대 12초 재생을 고려해 서버가 15초 여유 시간을 추가한다.
- 한쪽만 입력하고 다른 쪽이 제한 시간을 넘기면 입력한 쪽이 승리한다. 양쪽 모두 선출·행동하지 않으면 무승부다. 교체 선택 시간 초과와 기권은 패배로 처리한다.
- 일시적인 연결 끊김은 제한 시간 안에서 재접속할 수 있다. 만료 판정은 다음 서버 요청에서 처리되므로 두 사용자가 모두 종료했을 때 별도 백그라운드 작업을 실행하지 않는다.

## 향후 별도 테스트 서버 준비 시

현재 작업에서는 아래 설정을 실제 서비스에 적용하지 않았다.

1. 별도 테스트 Firebase 프로젝트에 서버 Admin 자격 증명을 준비한다. 클라이언트에는 관리자 키를 넣지 않는다.
2. 서버에 `RANKED_FIREBASE_PROJECT_ID`, `RANKED_FIRESTORE_PREFIX`, Admin 기본 자격 증명 또는 비밀값 `RANKED_FIREBASE_SERVICE_ACCOUNT_JSON`을 설정한다.
3. 클라이언트 `VITE_RANKED_ENABLED=true`, 서버 `RANKED_ENABLED=true`를 테스트 환경에만 설정한다. 브라우저는 같은 출처의 `/api/ranked`를 사용한다.
4. Firestore 레이팅 컬렉션은 클라이언트 직접 접근을 허용하지 않는다. Admin SDK만 서버에서 읽고 쓴다.
5. 실제 두 Google 계정으로 팀 동기화, 인증 만료, 재접속, 저장소 트랜잭션과 배포 환경의 지연을 검증한 뒤 운영 공개 여부를 결정한다.

운영용 API 어댑터는 Firebase ID 토큰과 취소된 인증을 확인하고 계정에 저장된 포켓몬·도구를 읽어 참가 팀을 구성한다. 기존 게임의 컬렉션 저장 자체는 클라이언트 동기화 방식이므로, 소유권의 완전한 부정 조작 방지에는 별도 서버 지급 원장 설계가 필요하다. 랭크 점수와 배틀 판정은 해당 클라이언트 저장 자료로 덮어쓸 수 없다.

Firestore 어댑터는 트랜잭션 내 모든 읽기를 먼저 완료한 뒤 변경을 저장한다. 엔진의 중첩 배열은 JSON 문자열로 보존하고 큰 연출은 별도 문서로 분할한다. 현재 방식은 소규모 테스트용 폴링 구조이며 대규모 운영의 부하·비용, 시즌 초기화, 전체 순위표, 보상 시스템은 이번 구현 범위에 포함하지 않는다.

관련 공식 문서: [Firebase ID 토큰 검증](https://firebase.google.com/docs/auth/admin/verify-id-tokens), [Firestore 트랜잭션](https://firebase.google.com/docs/firestore/manage-data/transactions).

## 검증 명령

```powershell
npm run validate:ranked
npm run build
```

UI 자동 검증은 기존 프로젝트와 동일하게 `promo`의 Playwright 런타임을 사용한다. 새 체크아웃에서는 먼저 `npm install --prefix promo`를 실행한다. 프로토콜과 저장소 검증의 세부 내용은 [레이팅 서버 문서](ranked-server.md)를 참고한다.
